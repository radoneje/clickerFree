# Развёртывание и сопровождение

## Утверждённый способ

GitHub → подключение к серверу по SSH → `git pull` → установка зависимостей → сборка → миграции при необходимости → перезапуск через PM2 → проверка работоспособности.

Используется существующий Nginx. Docker, Caddy и GitHub Actions для деплоя не используются. Автоматического обновления после отправки в `main` нет.

Этот документ — план: приложение, команды npm и конфигурация PM2 ещё не созданы. Команды ниже нужно реализовать и проверить до первого развёртывания.

## Что потребуется для первого запуска

- Адрес сервера и SSH-доступ под отдельным пользователем приложения.
- GitHub-репозиторий и доступ сервера к чтению репозитория.
- Домен, DNS и действующий HTTPS в Nginx.
- Поддерживаемые Node.js LTS, npm, PM2 и PostgreSQL.
- Приложения VK ID и Яндекс ID с production callback URL.
- Секреты сессий, подписи приглашений и настройки базы вне Git.
- План резервного копирования и место хранения копий отдельно от сервера.

Серверные процессы запускаются без root. Предлагаемый путь проекта — `/srv/clickerfree`, настройки — `/etc/clickerfree/production.env`. Реальные пути и порты фиксируются после осмотра сервера. Доступ к файлу секретов имеет только пользователь приложения и администратор.

## Nginx и PM2

Nginx отправляет обычные страницы в `127.0.0.1:3000`, `/api/` и `/socket.io/` — в `127.0.0.1:3001`. Для Socket.IO нужны HTTP/1.1, Upgrade/Connection и таймаут больше настроенного heartbeat; polling не должен кэшироваться. Порты приложений слушают только loopback. Подключить ограничения запросов и очистку журналов из [политики защиты](security.md).

В `ecosystem.config.cjs` предусмотреть два процесса: `clickerfree-web` и `clickerfree-api`. API работает в одном экземпляре, без cluster, до появления распределённой координации. Лимиты памяти, ротация журналов, корректное завершение соединений и автозапуск PM2 после перезагрузки обязательны.

## Порядок обновления

1. Проверить чистоту рабочего дерева, состояние сервиса, свободное место и доступность базы. Не удалять серверные изменения автоматически.
2. Зафиксировать текущий SHA и проверить резервную копию перед изменением схемы.
3. Получить утверждённую ветку командой `git pull --ff-only`. При расхождении истории остановить обновление и выяснить причину.
4. Установить зависимости из lock-файла и выполнить проверки/сборку.
5. Прочитать миграции; выполнить только совместимые с работающей версией. Разрушительные изменения требуют отдельного плана переноса данных.
6. Перезапустить процессы PM2 с актуальным окружением.
7. Проверить публичный сайт, API, соединение воркера и журналы. Зафиксировать SHA, время и результат обновления.

Планируемые команды из корня проекта:

```sh
git status --short
git rev-parse HEAD
git pull --ff-only origin main
npm ci
npm run check
npm test
npm run build
npm run db:migrate
pm2 restart ecosystem.config.cjs --env production --update-env
pm2 status
```

Перед использованием необходимо убедиться, что рабочая ветка — `main`, а секреты загружены предусмотренным механизмом. Команду миграции выполнять только после проверки состава изменений. Сборка должна сохранять предыдущие рабочие артефакты до переключения процессов; нельзя затирать обслуживаемый каталог Next.js в ходе сборки. Предусмотреть временный каталог и замену после успешной сборки.

Перезапуск API прерывает соединения; воркеры и пульты переподключаются и заново проходят авторизацию. Обновления проводить вне известных активных выступлений. Нулевое время простоя в первой версии не обещается.

## Проверки и откат

Предусмотреть `/api/health/live` и `/api/health/ready`: первый проверяет процесс, второй — доступность базы и применённую схему, без выдачи секретов. После рестарта проверить оба endpoint, русскую и английскую страницы, вход и тестовое управление на выделенном компьютере.

При неудаче вернуть предыдущий проверенный код и артефакты, затем перезапустить PM2. Откат кода не откатывает схему автоматически. Миграции должны поддерживать предыдущую версию приложения; при несовместимом изменении применять заранее подготовленный план, не восстанавливать базу поверх новых пользовательских данных без оценки потерь.

## Выпуск воркеров

Сборки Windows и macOS выполняются отдельно на соответствующих ОС. Указать версию приложения и протокола, прогнать тесты, проверить разрешения и чистую установку. Подписать исполняемые файлы и манифест релиза; для macOS предусмотреть notarization. Не предлагать пользователю отключение системной защиты как штатный сценарий.

Файлы публикуются вручную в GitHub Releases, затем проверяются скачивание, контрольная сумма и подпись. Только после этого релиз отмечается доступным в базе сервиса. Повышение минимальной версии — отдельное административное действие с записью в журнал и понятным сообщением на обоих языках.

## Резервные копии

Ежедневная копия PostgreSQL с шифрованием и хранением вне VPS; стартовая политика — 14 ежедневных и 4 еженедельные копии. Отдельно сохраняются необходимые конфигурации и ключи с ограниченным доступом. Не реже раза в месяц проверять восстановление в изолированной базе. Настроить уведомления об ошибках копирования и истечении TLS-сертификата.
